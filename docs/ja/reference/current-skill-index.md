# スキル一覧

このページでは、`specbind install`がプロジェクトに配置する製品管理のスキルを
まとめます。スキルが作成・管理するファイルは[成果物一覧](./current-artifact-index.md)を
参照してください。

## スキルの置き場所と呼び出し方

| エージェント | 置き場所 | 呼び出し方 |
| --- | --- | --- |
| Codex | `.agents/skills/sb-*/` | `$sb-*` |
| Claude Code | `.claude/skills/sb-*/` | `/sb-*` |
| generic | `.agents/skills/sb-*/` | ホストのエージェントに従う |

どのエージェントにも同じ15個のスキルが配置されます。Codexとgenericは
`.agents/skills/`を共有するので、両方を選んでも各スキルは1つだけ配置されます。

## 普段の流れで使うスキル

ライフサイクルの順に並べています。全体の関係は[基本概念](../guide/concepts.md)を
参照してください。

| スキル | 使う場面 |
| --- | --- |
| `sb-configure` | プロジェクトの設定を見直す・変更する、またはSpecBindをアップデートする。 |
| `sb-steering` | プロジェクトで長く維持する方針（Steering）を作成・更新する。 |
| `sb-discovery` | 変更を始める。スコープを確認し、MilestoneとSpecを作成する。 |
| `sb-plan` | 1つのSpecまたはMilestone全体（`--all`）のRequirements、Design、Tasksを計画する。共有Contractの変更（`--shared`）も準備する。 |
| `sb-contract-review` | Tasksの前に、Milestone内のすべてのContractをまとめてレビューする。 |
| `sb-implement` | 1つのRoadmap項目を、Taskごとのレビューを含めて実装する。 |
| `sb-validate-implementation` | 完了したSpecをRequirementsに照らして検証し、`GO`なら完了を記録する。 |
| `sb-release` | Milestoneをリリースする。バージョンの紐付け、公開、検証、確定処理を行う。 |
| `sb-drive` | Milestone内で安全に進められる作業をまとめて進め、リリースの手前で止まる。`--replan`を付けると範囲内の再計画も任せられる。 |
| `sb-status` | 現在の状態と、次に実行できる操作を表示する。読み取り専用。 |

## 必要なときに使うスキル

`sb-drive --replan`では、許可された再計画によって古くなった完了記録を自動で
取り下げられます。Driveが再計画前後の証拠を確認し、`sb-validate-implementation`に
1件ずつ委譲します。担当スキルが取り下げだけをコミットした後、Driveは残りの実装を
再開し、Milestone全体の作業が終わってから改めて検証します。以前から古かった記録、
ほかの不整合、引き継ぎ情報の欠落、対象ファイルの未コミット変更がある場合は、
この自動回復を停止します。通常の完了記録の取り下げには、引き続き確認が必要です。

複数のSpecが最終検証に進める場合、Driveは対象をまとめて1つの検証担当へ渡します。
担当は同じコミット時点で各Specを検証し、すべて合格してから完了記録を受理して
まとめてコミットします。これにより、後のSpecの受理で先の完了記録が古くなることを防ぎます。

SpecのTaskでは、既定で`sb-implement`の回復はユーザーが許可した実行・再開ごとに最大3回です。
許可された再計画や、
レビュー対象を訂正した再レビューもこの回数に含みます。修復後は、独立した評価で
以前の所見がすべて解消し、新しい所見だけが残った場合に限って続行します。
同じ所見が残る場合や解消を確認できない場合、3回目の後にも所見が残る場合は停止します。
残り回数は担当間の引き継ぎでも維持します。上限による停止を報告した後、その作業の
再開をユーザーが明示的に依頼すると、新しい回復枠を開始できます。対象が明確なら
「続けて」「更新したので再開して」で十分で、特別なリセット文言や追加確認は不要です。
最初の1回では以前の未解決所見にも再挑戦できますが、その後は同じ独立評価の続行条件を
適用します。以前の所見・失敗した方法・検証証拠を保持し、過去の累積回数が不明なら
不明のまま引き継ぎます。自動再委譲、セッション変更、Taskの再割当て、バージョン更新
だけでは枠を更新しません。対象範囲・承認・外部入力・検証の条件は変わりません。
Direct項目の回復には従来の別の上限を適用します。

独立評価で前進を確認できる間は3回を超えて続けたい場合、`sb-implement`または
`sb-drive`に`--recovery progress`を指定します。既定は`--recovery bounded`です。
これはSkillの引数で、CLIのフラグやプロジェクトに保存する設定ではありません。
「前進している限り回数制限なしで進めて」と明示しても同じ扱いです。単なる「続けて」では
選択されません。次の回復へ進むには以前の所見がすべて解消している必要があり、一部だけの
改善、所見の再発、対応関係が不明な場合は停止します。回数と履歴は引き継ぎでも保持します。
選択はその実行・再開だけに適用され、新たな実行・再開では再び指定しない限り既定に戻ります。
Direct項目、Design、Contractレビュー独自の上限は変わりません。

| スキル | 使う場面 |
| --- | --- |
| `sb-gap-analysis` | 計画の前に、予定している変更と現在のコードを比べ、結果をResearchとして残す。 |
| `sb-validate-design` | Designを独立して検証する。`sb-plan`はDesignの作成後に自動で実行する。 |
| `sb-review-task` | 実装済みの1つのTaskを差分からレビューする。修正はしない。 |
| `sb-debug` | 止まった実行の根本原因を調べて分類する。修正はしない。 |
| `sb-verify-completion` | 「完了した」という主張を新しい証拠で確認する。ライフサイクルの状態は変えない。 |

Design検証に必要な調査を実行できない場合、検証担当はDesignの判定を出さず、
`BLOCKED / ENVIRONMENT`で停止します。レビュー環境を修復してから検証を再開します。
この停止では、Planは作成者にDesignの修正を求めず、修正回数も消費しません。
レビューを実行した結果、Designが不十分だと分かった場合は、従来どおり`NOT_READY`です。

## 一時的なスキル

| スキル | 使う場面 |
| --- | --- |
| `sb-adopt` | 既存実装からSpecを確立する。`specbind install --with-adoption`のときだけ配置され、確立が完了すると自動で削除される。[既存実装からSpecを確立する](../guide/adopt-existing.md)を参照。 |

## Codex用のメタデータ

Codexには、追加で`.agents/skills/<skill>/agents/openai.yaml`が配置されます。
Codexの画面で使う表示名（`SpecBind Plan`など）、短い説明、依頼の例を定義する
ファイルです。スキルの呼び出し方は変わりません。
