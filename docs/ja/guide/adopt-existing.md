# 既存実装からSpecを確立する

動くコードはあるものの、信頼できる仕様がないプロジェクトでは、`sb-adopt`を使って
現在の実装からSpecを確立できます。コードとテストを調べ、「今後も維持する振る舞い」を
確認したうえで、Requirements（要件）、Design（設計）、Contract（責任範囲や接続点の契約）
にまとめます。

完成するのは、指定した既存バージョンを表すSpecと、その確立の記録です。この記録を
**ベースライン**と呼びます。Tasksの作成、実装の変更、プロダクトのリリースは行いません。
次の変更からSpecBindを使い始めたい場合は、[既存プロジェクトで始める](./start-existing-project.md)
を参照してください。別のSDD製品からの移行も、この手順の対象外です。

実装にある振る舞いが、そのまま要件になるわけではありません。維持すべき仕様なのか、
内部の実装詳細なのか、バグの疑いがあるのかを分け、判断が必要な点は提案で確認します。

## 手順の見通し

1. 一時スキル`sb-adopt`を導入し、Steeringと共通設定を整える。
2. 対象範囲と既存バージョンを指定して、調査を依頼する。
3. Specの分け方と維持する振る舞いの提案を確認する。
4. エージェントがSpecの作成・検証とベースラインの確定まで進める。

設定の見直しは、調査を始める前に済ませます。調査開始後の確認は、原則として手順3の
提案に対する1回です。Specの意味を左右する不明点や検査の失敗があれば、途中でも停止します。

## 1. 導入と設定を済ませる

新しくSpecを確立するには、永続的なSpecも進行中のMilestoneもないプロジェクトが必要です。
Milestoneは、今回確立するSpecをまとめて管理する単位です。

### 一時スキルを導入する

SpecBindを`--with-adoption`付きで[インストール](./install.md)します。すでに導入済みなら、
変更をコミットして作業ツリーをクリーンにしてから、次を実行してください。

```sh
specbind install --dry-run --with-adoption
specbind install --with-adoption
```

最初のコマンドで配置計画を確認し、次のコマンドで適用します。配置されたファイルを
コミットしてから、エージェントのセッションを開き直してください。

### Steeringを整える

Steeringは、プロダクトの目的、技術上の制約、責任の配置など、プロジェクト全体で共有する
方針です。不足している場合は、`sb-configure`に初期設定のレビューを依頼します。

```text
$sb-configure 既存実装からSpecを確立するために、このプロジェクトの初期設定を
見直してください。必要なSteeringの作成から始めてください。
```

`sb-configure`は現在の設定を確認し、必要に応じてSteeringの作成・更新を`sb-steering`へ
引き継ぎます。提案されたSteeringを確認し、コミットしてください。

### テンプレートと共有ルールを見直す

Steeringが整ったら、Requirements・Designテンプレートと共有ルールがプロジェクトに
合っているかを確認します。

```text
$sb-configure 確定したSteeringとリポジトリの事実を使い、このプロジェクト向けに
Requirements・Designテンプレートと共有ルールを見直してください。
```

追加でエージェントや運用アダプターなどを見直す場合は、対象ごとに依頼を分けます。
`sb-configure`は変更ごとに設定を再確認し、必要な後処理まで行います。
Designテンプレートを増やすのは、独立した責任を繰り返し記述する必要がある場合です。
技術名が違うという理由だけで増やす必要はありません。設定変更が既存のSpecや
ライフサイクル成果物を自動的に調整することもありません。

詳しくは[カスタマイズ](./customization.md)を参照してください。
設定変更をすべてコミットし、作業ツリーがクリーンになったら次へ進みます。

## 2. 範囲と既存バージョンを指定する

依頼には、次の2点を含めてください。

- **対象範囲**：リポジトリ全体、または具体的な領域。
- **既存バージョン**：現在のコードが表しているプロダクトのバージョン。次にリリースするバージョンではありません。

たとえば、リポジトリ全体を対象にする場合は次のように依頼します。
`v2.4.0`は、対象プロジェクトの既存バージョンに置き換えてください。

```text
$sb-adopt このリポジトリ全体の既存実装を、既存バージョンv2.4.0のSpecとして
確立してください。現在のコードとテストを証拠として調査し、成果物を作る前に
Specの分け方と、今後も維持する振る舞いを私に確認してください。
```

`sb-adopt`は事前検査を行い、調査の基準となるGitリビジョンを固定してから、コードと
テストを調べます。**完了するまで、実装、テスト、依存関係、設定、Steeringを変更しないでください。**
調査中にソースが変わると、新しいクリーンなリビジョンからやり直す必要があります。

## 3. Specの提案を確認する

調査結果は、1つの提案にまとまります。次の点を確認してください。

- 対象範囲と既存バージョンが正しいか。
- 各Specの責任範囲と、維持する振る舞いが意図に合っているか。
- 根拠となるコードやテスト、Spec間の依存関係が妥当か。
- 共有リソースがある場合、その範囲と保証、利用するSpecが妥当か。
- 回答が必要な不明点、後回しにできる不明点、バグの疑い、対象外が明確か。

実装とSteeringに違いがある場合も、ここで扱います。維持する仕様の意味を決めるために
回答が必要な問いは、確認前に解決します。提案に修正が必要なら、この段階で伝えてください。
**提案を明示的に確認するまで、SpecやMilestoneは作成されません。**

## 4. 作成・検証から完了まで進める

提案を確認すると、`sb-adopt`は同じ依頼の中で次の処理を進めます。

```text
Roadmap、Spec、調査用のBrief・Researchを作成
  → Requirementsを作成・承認
  → DesignとContractを作成し、独立したDesign検証を経て承認
  → Milestone全体のContract Review
  → ベースラインを確定
```

通常のフェーズごとの確認では停止しません。依存するSpecがある場合は、依存関係の順に
Designを進めます。すべてのDesignとContractがそろってから、全体の整合性を確認する
Contract Reviewを行います。

完了すると、次の成果物が残ります。

| 成果物 | 残る内容 |
| --- | --- |
| 各Spec | Requirements、Design、Contractと、元のリビジョン・既存バージョンの来歴 |
| 各Specの`log.md` | `ベースライン <version>`の記録 |
| `baselines/` | RoadmapとContract Reviewの履歴 |

一時的なBrief・Researchと調査記録は削除され、進行中のMilestoneは閉じます。
導入時だけ使う`sb-adopt`も、設定済みの全エージェントから削除され、
`.specbind.json`では無効になります。

以後は、確立したSpecを通常の既存Specとして扱えます。次の変更は
[既存プロジェクトで始める](./start-existing-project.md)の手順で進めてください。

## 途中で止まったとき

### セッションが終了した

進行中の確立作業を再開することを、`sb-adopt`に明示して依頼します。

```text
$sb-adopt 進行中の、既存実装からSpecを確立する作業を再開してください。
```

再開には、保存された状態が整合し、作業ツリーがクリーンで、固定したソースが変わっていない
ことが必要です。事前検査に通れば、未完了の工程から続けます。
提案の作り直しや、承認済みフェーズの繰り返しは行いません。

### 不明点やバグの疑いが見つかった

回答によってSpecの意味が変わる問いは、そのSpecの作業を止めます。独立した別のSpecは
進められますが、全体のContract Reviewと完了処理は回答を待ちます。
どの回答でも現在のSpecの意味が変わらない問いだけ、後回しにできます。

バグの疑いは、リビジョンと根拠の位置を添えて扱います。後回しにする指摘の保存先を定める
アダプター（`deferred.md`）が有効なら、その指示に従い、Milestone作成後に確認済みの
ローカル保存先へ記録します。自動的にバグや要件として確定することはなく、この手順内では
修正しません。プロジェクト外への送信には、別途許可が必要です。

### 実装の変更が必要になった

通常の変更は、Specの確立が終わってから新しいMilestoneで進めます。
対象範囲の変更や、調査基準のリビジョンを途中で差し替えること（rebaseline）はできません。
緊急の変更で先に中断する必要がある場合は、次のコマンドを使います。

```sh
specbind milestone reverse abandon --milestone-id <id>
```

中断処理の変更をコミットしてから、通常のDiscoveryで変更を進めます。その後、
新しいクリーンなリビジョンからSpecの確立をやり直してください。
ライフサイクル状態を手作業で削除しないでください。

### 完了後にスキルの削除だけが保留になった

ベースラインは確定済みです。完了処理の変更をコミットしてから、次を実行します。

```sh
specbind install --without-adoption
```

スキルを削除するために、ベースラインの完了処理を再実行してはいけません。

## 状態や記録を詳しく確認する

以下は、エージェントの報告や保存された成果物を確認するときの補足です。
通常の操作では、ここにある状態を手作業で設定する必要はありません。

### リバース確立の状態

既存実装からSpecを確立する処理を、内部では「リバース確立」と呼びます。
`specbind adoption preflight`が返す`source_revision`が調査の基準です。
Roadmapは`reverseSpecs`を使い、`newSpecs`、`specUpdates`、`target_release`は使いません。
各Specには、次の来歴が残ります。

```yaml
establishment:
  kind: reverse
  source_revision: <固定したGitリビジョン>
  baseline_version: <既存のプロダクトバージョン>
  milestone_id: <リバースMilestone>
```

Requirements、Design、Design検証、Contract Reviewは通常の担当スキルが処理します。
Designが承認されると、Specは`adoption_ready`になります。`tasks.yaml`は作成せず、
実装や実装検証、リリースアダプターの実行、タグ作成、公開も行いません。

### Contractの検査と完了処理

後続Specが先行Designの完了を待っていて、まだContractを持たない間に限り、Designの
検査ではContractグラフ全体を暫定状態として扱えます。それ以外のグラフエラーは許容しません。
Milestone全体のContract Reviewでは、完全なグラフが必要です。

すべてのSpecが`adoption_ready`になり、Contract Reviewが最新の成果物に対して有効
（fresh）になると、`sb-adopt`が次を実行します。

```sh
specbind milestone reverse finalize --log-entries <path-or->
```

この完了処理は、来歴を保持したまま各Specの進行中の変更状態を閉じます。
作成される履歴はSpec確立の記録であり、プロダクトリリースの記録ではありません。
