# PlanとDriveでMilestoneを進める

このページでは、複数のSpecやDirect項目を含む進行中のMilestoneを、計画の確定から
実装検証の完了までまとめて進めます。最初に`sb-plan --all`で計画をレビューし、
その後`sb-drive`で安全に到達可能な作業を進めるのが通常の推奨経路です。

Driveはリリースを実行しません。局所的な問題があっても独立した作業が残っていれば
そちらを進め、すべての到達可能な作業が尽きた時点で、必要な判断をまとめて報告します。

## 1. 前提を確認する

先にDiscoveryでスコープ、Spec、Direct項目、依存関係を確認し、進行中のMilestoneを
作成しておきます。開始時には作業ツリーに未コミットの変更がないことを確認してください。

```text
$sb-status
```

Driveは現在の状態をCLIから毎回読み直します。以前の会話や前回のDrive報告を、進捗の
正規情報として引き継ぎません。

## 2. Milestone全体を計画する

```text
$sb-plan --all
```

Planは、対象となる全SpecのRequirements、依存順のDesignと独立検証、Milestone全体の
Contractレビュー、Tasksを進め、Tasks承認後に停止します。Direct項目はSpec成果物を
持たないため、この計画対象には入りません。

同じ作業ツリーでは、成果物を作成するフェーズを承認とコミットまで1件ずつ進めます。
Designも、1つのSpecの独立検証と承認を終えてから次のSpecに着手します。
RequirementsとTasksはRoadmapの依存関係によらず着手できますが、同時にファイルを
編集するわけではありません。未完了の草稿が残った場合は、担当が変更を確定できるまで
別Specへの切り替えを停止します。

実行の最初に、Requirements、Design、TasksのGate承認をこの名前付き実行へ委任するか
確認されます。委任は確認箇所をまとめるだけで、レビューやCLI検査を省略しません。

計画を先に分けることで、Milestone全体の振る舞い、設計境界、実行順を実装前にまとめて
レビューできます。なおDriveを計画途中から実行することもできますが、通常のDriveには
Gate承認権限がありません。必要な承認がなければ、その項目を保留して別の到達可能な
作業を探します。

## 3. 到達可能な作業をDriveする

```text
$sb-drive
```

通常の進行では、Driveは`specbind milestone status --json`が示す着手可能な操作を選び、1回に
1つの所有ワークフローへ委譲します。RequirementsやDesignを自身で書いたり、Taskを
まとめて完了扱いにしたりはしません。

Driveの依頼には、検証対象のSpecが`GO`になった場合の完了記録と、Gitアダプターに従う
コミットまで含まれます。完了記録のためにもう一度確認する必要はありません。ただし、
「完了記録の前で止める」「変更しない」などの明示的な指定を優先します。
計画のGate承認とリリースには、それぞれ別の権限が必要です。

代表的な委譲先は次のとおりです。

| 状態 | 所有するワークフロー |
| --- | --- |
| 未完了の計画 | `sb-plan`と各計画フェーズ |
| Contractレビュー | `sb-contract-review` |
| 実装 | `sb-implement <item-id>` |
| Spec全体の実装検証 | `sb-validate-implementation <spec-id>` |
| リリース前 | 状態を報告して停止 |

各委譲後に、DriveはGitの作業ツリーとMilestoneの状態を読み直します。現在のバージョン
では、状態を変更するワークフローを並列実行せず、1件ずつ進めます。

### 実装中の再計画も任せる

```text
$sb-drive --replan
```

このオプションを指定すると、承認済みRequirementsと既存のMilestoneスコープの範囲で、
Design・Contract・Tasksの修正を委譲できます。指定自体が承認になるため、委譲の確認を
もう一度求められることはありません。自然文で再計画の委譲を明示しても同じ扱いです。

Driveは問題を計画担当へ返し、担当が必要なGateの無効化、成果物の修正、独立検証、
Contractレビュー、再承認を行います。その後、Driveは同じ実行内で実装と検証を再開します。
変更内容は報告しますが、計画を変更したという理由だけでは停止しません。

この再計画で別の参加Specの完了記録が古くなった場合、Driveは変更前のクリーンな
コミットと実際の計画差分を照合し、`sb-validate-implementation`に完了記録だけの
取り下げを委譲します。取り下げは1件ずつ独立したコミットに残します。その後、残りの
実装を再開し、Milestone全体の作業が終わってから改めて検証します。この後処理で追加の
確認は求めません。ただし、以前から古かった記録、ほかの不整合、履歴の欠落、対象の
状態ファイルの未コミット変更がある場合は、自動の取り下げを停止します。
Requirements・Design・Tasksと、それらの承認は保持します。

Designの変更では、Milestone全体のContractレビューとTasks承認をやり直す場合があります。
完了済みの作業も再実装・再検証の対象になり、変更のない作業は証拠が引き続き有効な場合に
進捗を維持します。実装途中の変更は、その実行によるものと特定できれば保持したまま
再計画できます。計画担当はその実装変更に触れず、実装担当へ戻します。無関係な変更や
競合する変更がある場合は引き続き停止します。

Requirements、Milestoneの対象範囲や依存関係、対象外Specの変更、外部互換性や移行に関する
未決の判断は、引き続きユーザーに確認します。レビューと再試行の上限は維持され、リリースも
別の操作です。従来どおり巻き戻しの確認を受けたい場合は、`--replan`を付けずに実行してください。

### 回復が前進している間は続ける

```text
$sb-drive --recovery progress
$sb-implement <item-id> --recovery progress
```

1つ目は今回のMilestone実行で到達するSpecのTask、2つ目は指定した項目のTaskに適用します。
Claude Codeでは、先頭を`/sb-drive`または`/sb-implement`に置き換えます。
これはSkillの引数で、`specbind` CLIのフラグではありません。
「独立評価で前進を確認できる限り、回数制限なしで進めて」と明示しても同じ扱いです。
単なる「続けて」では`progress`は選択されません。新たな実行では最大3回の既定モード
`bounded`を使い、同じ実行の継続では、すでに選択したモードを維持します。

`progress`では、以前の所見が独立評価ですべて解消し、新しい問題だけが残る場合に、
4回目以降も続行できます。一部だけの改善、同じ所見の残存・再発、履歴が不明な場合は
引き続き停止します。モードと使用回数は担当間で引き継ぎ、プロジェクトの既定値としては
保存しません。新たな実行・再開では、再び指定しない限り`bounded`に戻ります。
実行途中で`--recovery bounded`へ戻しても使用回数は保持します。すでに3回以上使い、
問題が残っている場合は、それ以上の修復を停止します。

Direct項目やDesign・Contractレビュー独自の上限は変わりません。再計画、スコープ変更、
リリースの権限も付与しません。上で説明した範囲内の再計画も任せる場合は、
`--replan`と組み合わせてください。

## 4. 保留と停止の違いを理解する

複数のSpecが最終検証に進める場合は、1つの検証担当が同じコミット時点で各Specを
検証します。すべて合格してから完了記録を受理し、まとめてコミットします。
必須の検証が失敗したり実行できなかったりした場合は、全対象の受理を止めます。
ほかのSpecに修正が必要なまま、合格したSpecだけを先に完了扱いにはしません。

受理前にHEADが変わるか未コミットの変更が生じた場合は、完了を記録せず、対象Spec、
検証時と現在のコミット、変更されたパスを報告してDriveを停止します。途中で入った
変更を整理したあと、もう一度Driveを実行してください。新しい検証担当が現在の対象を
まとめて事前検査からやり直し、必要なチェックと各Specの評価を実施します。
前回の受理候補や判定は再利用しません。

ある項目が進められなくても、Driveが即座に実行全体を止めるとは限りません。

```text
項目Aに判断が必要
  -> Aとその依存先を保留
  -> 独立した項目Bが安全に進められるなら継続
  -> 到達可能な作業が尽きたら、Aの判断を報告
```

Driveは、問題の原因と実行全体の判断を分けます。

| 原因の例 | 扱い |
| --- | --- |
| `HUMAN_DECISION` | スコープ、意味、承認、不可逆な結果をユーザーが判断するまで保留 |
| `BLOCKED` | 所有ワークフローが進行不能と確定した項目を保留 |
| `WAITING` | 依存先やMilestone全体の障壁が解消されるまで待機 |
| `REROUTABLE` | RequirementsやDesignなど、より上流の所有フェーズへ戻す |
| `EXTERNAL_BLOCK` | 環境や外部前提を満たせないため保留または停止 |

別の安全な操作があれば`CONTINUE_ELSEWHERE`、無ければ`STOP_RUN`になります。未完了の
DesignはContractレビューを止めますが、別SpecのDesignまでは止めません。未完了の実装は
その依存先とMilestone全体の完了を止めますが、独立した実装までは止めません。

作業ツリーに部分的、拒否済み、無関係、または所有者不明の変更が残った場合は例外です。
別項目へ安全に切り替えられないため、Driveはリセットやstashをせず実行全体を止めます。
ただし、上記の再計画で同じ作業の実装変更を保持して引き継ぐ場合は継続できます。
その変更を残したまま独立した別の作業へ切り替えることはできません。

## 5. Driveの結果を確認する

Driveは最後に、次の内容をまとめて報告します。

- 到達したMilestoneの境界
- 完了した所有ワークフローと増えた正規の状態
- 保留項目、その原因、影響を受ける依存先
- 再開に必要な判断または外部条件
- 次に安全に実行できる操作
- リリースを実行していないこと

保留一覧はその実行だけの報告で、永続的なキューではありません。判断や外部条件を解決したら、
もう一度`$sb-drive`を実行します。Driveは最新状態から到達可能な作業を再構築します。
再計画の回復途中から再開する場合は、変更前の証拠、完了した取り下げのコミット、
Taskの残り回復回数を含む前回の引き継ぎも渡してください。現在の状態だけでは、
これらの情報を復元できません。

Taskが回復上限で停止した場合は、たとえば「更新したので再開できるか確認し、
進められれば進めて」と、その作業の再開を明示的に依頼できます。そのTaskについて
既定では追加確認なしで最大3回の新しい回復枠が始まります。Driveは指示と過去の履歴を実装担当へ
渡し、担当は現在の証拠を独立評価してから再挑戦します。対象のblockedなTaskを
再開できますが、依存待ちや無関係な変更は無視できません。以前の所見や失敗した方法は
保持し、今回の使用回数だけを0から数えます。旧履歴の累積回数が不明なら、不明のままです。
自動再委譲、コンテキスト圧縮、Taskの改名、SpecBindの更新だけでは枠は増えません。
同じ指示を次の引き継ぎでもう一度使って枠を更新することもできません。
対象範囲や承認の境界は引き続き守ります。

## 6. リリース前で止める

すべての実装検証が完了すると、次の境界はリリース準備になります。対象バージョンが
未設定なら、Driveは勝手に選ばず人の判断として保留します。バージョンを明示して
リリース前の紐付けまで進める場合は、次のように依頼できます。

```text
$sb-drive --target-release 1.2.0
```

この指定でも、Driveは配布物の作成、公開、検証、確定処理を実行しません。状態が
`release_ready`になったところが完了境界です。公開するときは、結果を確認してから
[リリースする](./release.md)を別途実行します。

## この進め方を選ぶ場面

- 複数SpecやDirect項目を含むMilestoneを依存順に進めたい
- 局所的な判断待ちがあっても独立作業を続けたい
- Tasks承認後の実装と検証を、正規状態を確認しながら任せたい
- 中断後に、永続的なキューを保守せず最新状態から再開したい

各成果物を段階ごとに確認したい場合は、
[1件ずつ計画・実装する](./implement-step-by-step.md)を使ってください。
