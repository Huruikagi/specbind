# SpecBindをアップデートする

SpecBindのアップデートには、PCで実行する`specbind`バイナリの更新と、
各プロジェクトに配置された製品管理対象ファイルの更新があります。通常は、この2つを
`sb-configure`スキルにまとめて依頼します。

`specbind`自身がバイナリを置き換える自己更新コマンドはありません。バイナリは
インストールに使ったクライアント（通常はmise）が更新します。

## 1. 更新前の状態を整える

リポジトリの状態を確認します。

```sh
git status --short
```

次の状態が残っていると、更新は開始前に停止します。いつもの手順でコミットするなどして
解消しておいてください。

- ステージ済みの変更、名前変更、コピー、変更を含むサブモジュール
- `mise.toml`や`mise.lock`への未コミットの変更
- 製品管理対象（`.agents/skills/sb-*`など）への未コミットの変更

これら以外の未ステージの変更や未追跡のファイルは残して構いません。SpecBindは
そのパスを報告し、変更もステージもせずに保持します。

## 2. sb-configureに更新を依頼する

対象プロジェクトでコーディングエージェントのセッションを開き、更新を明示的に
依頼します。

```text
$sb-configure SpecBindを最新版へアップデートしてください。
```

特定のバージョンへ変更したい場合や、`mise.toml`でバージョンを完全に固定している
場合は、`SpecBindを1.5.1へアップデートしてください`のように、依頼に移行先の
バージョンを含めます。固定したバージョンは、明示しない限り進みません。

`sb-configure`は次の流れで更新を進めます。

1. 現在のバージョンを記録し、このプロジェクトのmise設定がSpecBindを管理して
   いることを確認する。
2. `mise upgrade`（またはバージョン指定時は`mise use`）でバイナリを更新し、
   `mise.toml`と`mise.lock`の差分を確認する。
3. Gitアダプターの方針に従い、バイナリ選択の変更だけを1つ目のチェックポイントとして
   コミットする。
4. 移行計画と`specbind install --dry-run`の計画を示してから、製品管理対象を更新する。
5. 新しく配置された`sb-configure`を読み直し、更新結果を検証して、製品管理対象の
   変更を2つ目のチェックポイントとしてコミットする。
6. 移行計画に残っている項目を、1件ずつ提案する。

2つのチェックポイントを分けるのは、バイナリの選択とプロジェクト内のファイル更新を
それぞれ確認・巻き戻しできるようにするためです。更新の依頼に`push`は含まれず、
リリースに関わる操作も行いません。

### 移行計画の項目を判断する

移行計画には、新しいバージョンで推奨される既存成果物の調整などが含まれます。
`sb-configure`は対象ごとの差分を示して確認を求めます。

- `required`の項目が残っている間は、移行作業全体の完了とは扱いません。
- `recommended`と`optional`の項目は、内容を確認したうえで見送れます。
- `blocked`と判定された項目は、表示された入力の問題を解消してから再開します。

更新の依頼そのものは、プロジェクトが所有する成果物の書き換えへの同意を含みません。
成果物の編集は、提案を確認した範囲だけで行われます。

## 3. 結果を確認する

最後に、`sb-configure`が次の内容を報告します。

- 更新前と更新後のバイナリのバージョン
- 2つのチェックポイントそれぞれの結果
- 保持したプロジェクト所有の設定と、手を付けずに残した無関係な変更
- 見送った移行項目と、残っている対象
- 停止した場合は、その場所と理由

Gitアダプターがコミットを許可していない場合は、報告された差分を確認し、プロジェクトの
通常の手順でコミットしてください。

更新済みのプロジェクトを取得したほかのメンバーは、`mise install`でロックファイルに
固定されたバイナリを導入できます。プロジェクト内の更新済みファイルはGitから
取得されるため、全員が更新をやり直す必要はありません。

!!! info "途中で中断した場合"
    移行計画の起点には、更新前のバージョンを使います。セッションが途切れて再開する
    ときは、`sb-configure`へ更新前のバージョンを伝えてください。現在のバージョンで
    代用したり、推測したりはしません。

## バージョンごとの移行項目 {#migration-items}

### 1.5.0: `description`の追加

1.5.0境界のRequirements・Design・Steeringと関連テンプレートに、`description`を
追加する推奨項目です。文書が継続して引き受ける責務を一文で記録します。既存1.x文書での
欠落は有効なままです。テンプレート更新は既存文書を書き換えず、説明の追加も承認や
鮮度の証拠にはなりません。

`spec list`はRequirements、`artifact list <spec>`はDesign、`steering list`は
Steeringのdescriptionを表示します。`missing`は項目の欠落、`invalid`は不正な
説明またはRequirementsの検証エラー、`unavailable`はRequirementsを一意に
取得できない状態です。一覧の説明は現在の文書内容であり、承認状態とは独立しています。

Designの新規作成時には、`artifact check <spec> <selector> --template <template>`で
選択したテンプレートの作成条件とdescriptionの完全な継承を確認できます。
責務を評価済みのSpec固有one-off文書には`--template design/main`を指定し、
その文書独自の責務を記します。この検査は既存文書の由来を証明せず、承認状態も変更しません。

### 要件の退役を使う前に

既存RequirementsのID移行は不要です。[要件の退役](./implement-step-by-step.md#retire-requirements)
を使う前に、インストール済みのスキルと、変更している場合はテンプレートの指示を
更新してください。旧バイナリは`_Retired_`マーカーを正しく解釈できないため、利用を
始めたあとは旧バージョンに戻さないでください。

## 更新されるものと保持されるもの

| 対象 | 所有者 | アップデート時の扱い |
| --- | --- | --- |
| `specbind`バイナリ | mise | `mise upgrade`または明示的な`mise use`で更新 |
| `.agents/skills/sb-*`、`.claude/skills/sb-*`などの製品管理対象 | SpecBind | `specbind install`で現在の埋め込み版へ置換。廃止された対象は計画に表示して削除 |
| `AGENTS.md`または`CLAUDE.md`のSpecBind管理ブロック | SpecBind | マーカー内だけを更新し、周囲の文章を保持 |
| `.specbind/settings/`以下のテンプレート、ルール、アダプター | プロジェクト | 既存ファイルを上書きしない。新しく追加された既定ファイルがなければ作成 |
| Specs、Roadmap、Gate、リリース履歴 | プロジェクト | `specbind install`では変更しない |

製品管理対象のスキルを直接編集する方法は、サポートされているカスタマイズでは
ありません。製品管理対象に未コミットの変更がある場合、SpecBindはその内容を推測して
上書きせず、競合するパスを表示して停止します。そのパスをコミット、スタッシュ、または
別の方法で解消してから計画をやり直してください。SpecBindが代わりにスタッシュを作る
ことはありません。継続して必要な方針は、製品管理対象のスキル内ではなく、プロジェクトが
所有する設定へ移してください。

## 例外: 手動で更新する

次の場合は、`sb-configure`に頼らず手動で更新します。

- バイナリをmise以外の方法でインストールした
- プロジェクトのmise設定がSpecBindを管理していないため、`sb-configure`が停止した
- エージェントを使わずに更新したい

### miseで手動更新する

1. 更新前に`specbind --version`を実行し、元のバージョンを記録します。
2. バイナリを更新します。完全に固定したバージョンを変える場合は、2行目の代わりに
   `mise use github:Huruikagi/specbind@<version>`を使います。

    ```sh
    specbind --version
    mise upgrade github:Huruikagi/specbind
    specbind --version
    ```

    `mise.toml`で`latest`を選んでいる場合、miseの`minimum_release_age`を満たす最新の
    安定版が選ばれます。詳しい挙動はmiseの
    [`upgrade`](https://mise.jdx.dev/cli/upgrade.html)と
    [`mise.lock`](https://mise.jdx.dev/dev-tools/mise-lock.html)の説明を参照してください。

3. `mise.toml`と`mise.lock`の差分を確認し、ほかの変更とは分けてコミットします。
   これをコミットする前に、次の`specbind install`を実行しないでください。
4. 移行計画と、製品管理対象の更新計画を確認します。

    ```sh
    specbind migration plan --from <更新前のバージョン> --json
    specbind install --dry-run
    ```

    移行先は実行中のCLIのバージョンです。計画の取得はファイルを変更しません。
    `install --dry-run`では、`create`、`replace`、`keep`と、廃止された対象に対する
    `remove`を確認します。`Unrelated changes: preserved`が表示された場合は、
    自分の既存作業であり、更新対象と重なっていないことも確認します。

5. 更新を適用し、差分を確認してコミットします。

    ```sh
    specbind install
    git status --short
    git diff
    ```

6. 移行計画に残っている項目は、[バージョンごとの移行項目](#migration-items)を
   参照して対応します。

### mise以外でインストールした場合

バイナリを導入した方法と同じインストーラーを再実行して更新します。利用できる
インストーラーと対応環境は
[READMEのInstall the CLI](https://github.com/Huruikagi/specbind#install-the-cli)を
参照してください。バイナリを更新したあとは、上の手順4以降と同じです。
