# 0167: Model template placeholders as named creation outputs

Status: Accepted

Supersedes: [Decision 0151](./0151-agent-bound-template-variables.md)

## Context

Decision 0151 described `{{name}}` as a variable bound to one value. That
language implies a scalar or previously available value even though the CLI
never resolves, stores, compares, or substitutes template content. Its actual
responsibility is only to prove that every named reference has one creation
instruction and that every named creation instruction has a reference.

The value-oriented model also makes a repeatable Markdown section look outside
the supported mechanism. A creation instruction may need to produce several
different component subsections, screen descriptions, or other authored
structures. The product does not need a loop language to support that case: one
named output can be the complete Markdown fragment generated by the agent.

The syntax and authoring contract should describe the boundary the product can
actually enforce without narrowing agent-authored output to scalar values.

## Decision

- Managed Markdown template bodies may contain named output references in the
  exact form `{{name}}`. A name is non-empty and contains no whitespace or brace
  characters; it may otherwise use Unicode.
- Every distinct output name has exactly one template-only instruction whose
  opening token sequence is `specbind:instruction create output=<name>`. Each
  declared output has one or more references, and one declaration may serve any
  positive number of references to that name.
- The `create output=<name>` instruction is the production recipe and authority
  for that named output. During one artifact materialization, the authoring
  agent follows the instruction once and may produce a short string or an
  arbitrary Markdown fragment, including several headings and subsections.
- The agent replaces every reference to one name with the same complete output.
  Independently produced content uses a different name. Variable item count and
  per-item differences may live inside one generated Markdown fragment; v1 does
  not add a separate loop, block, or iteration grammar.
- SpecBind validates invalid names and missing, duplicate, or unused output
  declarations mechanically. Only `create` instructions may declare an output.
  Output-like text inside managed instruction comments is explanatory and does
  not count as a reference.
- SpecBind does not whitelist names, produce content, invoke tools, compare
  repeated replacements, or perform substitution. There are no built-in
  outputs. The official `spec` and `artifact_id` outputs are ordinary creation
  outputs whose instructions tell the agent where to obtain their content.
- Named output references remain forbidden in Front Matter and other
  machine-owned identity or path fields. They are authoring primitives for
  Markdown bodies, not deferred structural identity.
- `template read` validates the resolved template inventory and returns the raw
  UTF-8 template, including every reference and instruction. Product-managed
  authoring Skills own materialization.
- Materialization follows the scoped-instruction lifecycle: the agent produces
  every named output, replaces every reference, omits `create`, preserves
  `maintain` and `consume`, and validates the completed live artifact before
  treating it as written successfully. An unresolved output reference or a
  leaked `create` instruction remains a live-artifact diagnostic.
- An output instruction cannot grant tool access or additional authority. If
  its recipe needs unavailable data, permissions, or a user decision, the agent
  follows the normal tool and interaction boundaries and stops rather than
  inventing content.

Decision 0150's fail-closed minimum-content checks remain accepted. Decision
0151's removal of `template render`, CLI-owned built-ins, and executable value
resolution also remains accepted; this Decision replaces its variable,
binding, and scalar-value model.

## Compatibility

`create output=<name>` is the preferred syntax. To preserve Decision 0144's
same-major forward-upgrade guarantee, the CLI also accepts the `create
bind=<name>` syntax published in `1.0.0` as a compatibility alias throughout
the 1.x executable line. The alias has the same validation and materialization
semantics as `output=`; it does not retain the former scalar interpretation.

Existing project-owned templates are not silently rewritten. Their owners may
preview and explicitly authorize reconciliation to the preferred terminology,
but an upgrade does not require that reconciliation before the templates remain
usable. Diagnostic codes published in `1.0.0` remain stable even where their
names use the former variable or binding terminology. Live artifacts contain
neither `create` instructions nor unresolved references, so they require no
migration.

## Consequences

- The CLI contract now names only what it proves: declaration-to-reference
  correspondence.
- Agents can use the same mechanism for an identity string, externally obtained
  text, or a generated multi-section Markdown fragment.
- Repeatable authored structure no longer needs an unvalidated angle-bracket
  placeholder merely because each generated subsection differs.
- The official Design scaffold uses a `components` output to demonstrate the
  fragment-producing case.
- Projects that still carry `create bind=<name>` continue to work in 1.x and
  may reconcile deliberately when adopting the preferred terminology.
