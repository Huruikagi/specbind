# 0124: Start public binary releases before 1.0

Status: Accepted

## Context

[Decision 0077](./0077-v1-installation-distribution-and-migration.md) made the
first public Rust release `1.0.0`. That was useful while "v1" named one fixed
target contract, but it now conflates three independent versions:

- the executable's public SemVer;
- the v1 product and workflow contract; and
- `schema_version: 1` in persisted structured artifacts.

The CLI implements the intended product surface, but distribution cutover,
cc-sdd migration, and public installation experience have not yet been proven
by released binaries. The README and user guide consequently still describe a
Preview. Claiming SemVer compatibility at `1.0.0` before users have exercised
that distribution would make ordinary stabilization unnecessarily expensive.

## Decision

### Product SemVer starts at 0.1

The public Rust release line starts with `0.1.0` and may use SemVer prereleases
such as `0.1.0-rc.1` while the release path is being exercised. The Cargo
package version and `specbind --version` are the executable version. A release
tag is exactly `v` followed by that version.

The v1 product contract and the version-one wire schemas remain unchanged.
They name interface generations, not a promise that the executable has reached
SemVer `1.0.0`.

During `0.x`, incompatible CLI, installed-asset, or artifact changes remain
possible when they are recorded in the changelog and the relevant accepted
decision. Persisted artifact compatibility must still be changed deliberately;
pre-1.0 is not permission to reinterpret an existing schema version.

### Primary distribution

GitHub Releases is the only primary distribution channel. Each release
contains exactly these native archives for the initially supported platforms:

| Target | Archive |
| --- | --- |
| Windows x64 MSVC | `specbind-v<VERSION>-x86_64-pc-windows-msvc.zip` |
| Linux x64 GNU | `specbind-v<VERSION>-x86_64-unknown-linux-gnu.tar.gz` |

Here `<VERSION>` is the Cargo version without a second leading `v`; for
example, `specbind-v0.1.0-x86_64-pc-windows-msvc.zip`. Each archive contains
the native executable, `README.md`, and `LICENSE`. `SHA256SUMS` covers both
archives and is mandatory.

A tag-triggered GitHub Actions workflow validates that the tag and Cargo
version match, runs the Rust verification suite on Windows and Linux, packages
and smoke-tests both archives, generates `SHA256SUMS`, and creates the release.
A SemVer prerelease tag is published as a GitHub prerelease. Publication fails
closed when an asset or checksum is missing.

### Installer boundary

The repository publishes `install.ps1` for Windows x64 and `install.sh` for
Linux x64. Both installers:

- select the latest non-prerelease GitHub Release when no version is supplied;
- require an explicit version to install a prerelease;
- download the matching archive and `SHA256SUMS`;
- reject a missing or mismatched checksum before extraction;
- install to the Decision 0077 default or an explicit install directory; and
- never edit a shell profile or persistent `PATH`.

Homebrew, WinGet, Scoop, crates.io installation, self-update, code signing,
notarization, macOS, and ARM binaries remain outside this release line until a
separate decision admits them.

## Consequences

- Early adopters get a reproducible binary installation path without a
  premature long-term compatibility claim.
- A later `1.0.0` is an explicit compatibility milestone rather than a name
  inherited from the internal v1 design target.
- Release tags, archives, checksums, Cargo metadata, CLI output, changelog, and
  installation documentation must advance together.

This decision supersedes only Decision 0077's statement that the first public
Rust release is `1.0.0`. Its platform, checksum, installation, migration, and
post-v1 channel boundaries otherwise remain in force.
